# Motion validation: pluggable validator, resolution owned by the state space

Motion validation is today four private `check_motion` copies (one per planner) with a hard-coded `× 0.1` oversampling factor, no user extension point, and nothing exposed to the bindings. We are replacing them with a public, pluggable motion validator modelled on OMPL's `MotionValidator`, designed once so that later extensions are additive rather than breaking. Binding users are the primary beneficiaries: a user validator checks a whole motion in one cross-language call instead of one call per interpolated state.

## Decisions

- **Resolution lives on the state space; checking strategy lives on the validator.** The space states how finely a motion must be inspected; a validator decides how to check (discrete inspection at the space's resolution, analytic, batched, …) and may ignore the space's resolution entirely. Matches OMPL (`DiscreteMotionValidator` only reads the space's `validSegmentCount`), and keeps resolution available to consumers that have no validator (path interpolation, densification).
- **Yes/no `check_motion` is the only required validator method.** OMPL's second overload (last valid state + fraction along the motion) is deferred until a planner needs it, and will arrive as a *provided* method returning the fraction (`Result<(), f64>`), defaulting to `Err(0.0)` on failure — sound because the start state is assumed valid. To keep that addition non-breaking, three things are fixed now: the trait documents from day one that the motion's start state is assumed valid; the trait stays object-safe (`Arc<dyn MotionValidator<S>>`); binding adapters treat user validators as objects with optional methods (Python `hasattr`, JS property check), never as bare callables.
- **Not copied from OMPL:** two mandatory overloads; valid/invalid counters in the base trait (a decorating validator can count when benchmarking needs it).
- **Attachment: a validation context, after OMPL's `SpaceInformation`.** It bundles the state space, the state validity checker and the motion validator (Discrete by default). `ProblemDefinition` holds the context *instead of* a bare space (never both, so the two cannot disagree), and planners stop taking a checker in `setup()`. Rejected: an extra `setup()` parameter (breaks every call site and makes users assemble the default validator themselves); a per-planner `set_motion_validator` (additive, but each consumer is configured separately, so a planner and the path simplifier can silently judge validity differently). The context grows only through additive builder methods (e.g. valid-state samplers later).
- **Compound resolution: maximum of component segment counts (OMPL).** The space gains `valid_segment_count(s1, s2)`, defaulting to `ceil(distance / longest_valid_segment_length)`; compound, SE2 and SE3 override it with the max over components. The previous single weighted-RMS length under-samples rotation: SE2 on [0,10]² at default settings inspects a 180° turn every 36° once `× 0.1` is gone (vs 9° per component); the `× 0.1` factor had been masking this.
- **No hidden oversampling; default fraction 0.01 (OMPL).** The `× 0.1` factor is removed; the default longest-valid-segment fraction drops from 0.05 to 0.01. Single spaces are inspected 2× more coarsely than before, compound spaces more finely. Migration note: set the fraction to 0.005 to reproduce the old single-space spacing. OMPL's extra segment-count factor is not adopted (the fraction covers it; addable later).

- **Validation is fallible: `is_valid` and `check_motion` return `Result<bool, _>`.** `Ok(false)` means invalid; `Err` means the checker itself failed, and planners abort with a planning error carrying the original failure. Probe against oxmpl-py 0.7.0 showed why `bool` is not enough in Rust: a Python callback that raised was printed and treated as invalid, so `solve()` still returned a path, Ctrl-C (`KeyboardInterrupt`) was swallowed, and a typo in the checker produced 286k lines of tracebacks over the full timeout before a misleading "no solution". OMPL can keep `bool` only because C++ exceptions unwind through the planner (OMPL's Python bindings raise immediately); Rust has no unwinding channel (and the wasm build is `panic="abort"`), so the error channel must be in the signature. Rejected: `bool` with deferred re-raise (still burns the whole timeout); a polled error slot on the context (every planner must remember to poll).
- **Validation traits are `Send + Sync`, cascading to `StateValidityChecker` and `StateSpace`.** The default validator holds both, so it can only be thread-safe if they are; adding the bound later is breaking, so it lands in the same breaking release. Rust implementers using `Rc`/`Cell`/`RefCell` must switch to `Arc`/`Mutex`/atomics. Python callbacks (`Py<T>`) already qualify. JS callbacks (`js_sys::Function`) never do: the JS adapters use `unsafe impl Send + Sync`, sound only on single-threaded wasm32, guarded by a `compile_error!` under `target_feature = "atomics"`.

- **Goals follow the same rules.** `Goal::is_satisfied` and `GoalRegion::distance_goal` become fallible and the goal traits gain `Send + Sync`, so a failing goal callback aborts planning exactly like a failing checker (the 0.7.0 binding adapters swallow goal-callback errors the same way: `false` / `INFINITY`).
- **Error shape.** Failures of user-supplied code (checkers, validators, goals — Rust or binding callbacks) are a `UserError = Box<dyn Error + Send + Sync>` — any Rust error converts with `?`, and the bindings box the original `PyErr`/`JsValue` so they can re-raise the user's own exception. They surface as `PlanningError::User(..)`, and goal sampling carries them via a new `StateSamplingError::User(..)` (`sample_goal` keeps its signature). `PlanningError` loses `PartialEq` (boxed errors are not comparable; tests already use `matches!`) and, with `StateSamplingError`, becomes `#[non_exhaustive]` so future variants are additive.
- **The context is named `SpaceInformation`,** as in OMPL, to keep translation from OMPL direct.
- **`ProblemDefinition` has no space field of its own;** the space is reached only through its `SpaceInformation`.

- **`SpaceInformation` is constructed with a required checker and frozen once shared.** `SpaceInformation::new(space, checker)` installs the discrete validator; OMPL's setter names are kept (`set_motion_validator`), but configuration needs exclusive access (`&mut` in Rust; in the bindings `Arc::get_mut`, raising if a `ProblemDefinition` already holds it). The space is shared into the `SpaceInformation`, not copied, and is frozen the same way. This departs from OMPL deliberately: OMPL silently installs an all-valid checker when none is set ("No collision checking is performed" is only a log warning) and keeps `SpaceInformation` mutable, so a PRM roadmap built under one validator can be queried under another, or a path solved under one validator simplified under another, with no signal. Mutability would also put synchronisation on the hottest path now that validation is `Send + Sync`. Cost: switching validator between queries means a new `SpaceInformation` (and a roadmap rebuild), which is the correct outcome.
- **`setup()` no longer takes a checker.** Rust: `setup(problem_def)`. The bindings drop `setup` entirely, since their planner constructors already receive the problem definition.
- **The default motion validator is always the discrete one.** OMPL's per-space specialised validators (e.g. Dubins) still step through the space's segment count and `interpolate`; they exist for speed, not correctness, so the discrete validator is correct for any space whose interpolation is correct. A per-space default can arrive later as a provided `StateSpace` method.

- **Binding protocol.** The state validity checker stays a plain function (`SpaceInformation(space, fn)`; JS's `StateValidityChecker` wrapper class goes). A user motion validator is a duck-typed object with `check_motion` / `checkMotion`, verified when set (missing method raises then, not mid-solve); later optional methods are detected by presence. Python ships `typing.Protocol` stubs, JS a TypeScript `interface`; no base class to inherit. Returns are strict: a non-boolean (Python `bool`/NumPy `bool_` accepted) raises instead of counting as invalid.
- **Resolution is fully exposed in both bindings:** all six spaces get the fraction setter, longest valid segment length, `valid_segment_count` and `interpolate`, so user validators can work at the space's resolution without re-implementing it. JS's `setLongestValidLineSegmentFraction` is renamed `setLongestValidSegmentFraction`.
- **Binding errors.** Python: `OxmplError(Exception)` base with `PlanningTimeout`, `NoSolutionFound`, `InvalidStartState`, `SamplingError`, `PlannerUninitialised`, `ConfigurationError`. JS: `OxmplError extends Error` with a `kind` field. A validation failure re-raises the user's original exception/value unwrapped (as OMPL does; `KeyboardInterrupt` stays itself).
